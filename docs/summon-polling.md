# 无缝联机的短轮询

Windows 无缝模式和 Linux BBSC 配方启动游戏服务时，显式传入 `--summon-interval 2`。游戏服务在 `ss.info` 中下发 `SummonDataGetListInterval2=2` 和 `SummonDataCreateInterval2=2`，替代原版的 35 秒搜索／30 秒发布间隔。普通模式只启动 shadNet，不使用这项设置。

## 什么时候产生请求

这是客户端请求间隔，不是服务器每两秒向所有玩家广播，也不是限制战斗同步每两秒一次。服务器只在收到请求时应答。

游戏进入在线、运行召唤搜索流程时，可能在玩家尚未摇铃前就查询匹配列表；本次实测已经观察到这种请求。因此本实现不是“只有房主摇铃后才启用短轮询”。列表查询、发布自己的召唤记录以及建立／加入房间是不同步骤，空闲列表查询不会单独触发自动召唤。游戏离线或退出后不再发送这些在线查询。

## 收益与代价

原间隔下的失败轮次中，基础信令已建立，但约五秒后连接失效；客机之后才读到召唤回应，随后进入清理和重试。在保持房主、客机、网络及诊断客户端不变的单次 2 秒对照中，仅一次激活便调用 JoinRoom：建房至服务端加入约 3.3 秒，加场景加载后约 15 秒，两人互见及移动正常。

这支持缩短轮询改善这一环境下的时序兼容，但不是所有慢入房问题的唯一根因。成功轮没有旧的 174 字节 claim 读取记录，不能据此声称已证明那份 HTTP 回应提早送达。交换房主、多组玩家和其他网络尚未完成同等回归。

更频繁的 HTTP 请求会增加客户端／服务器处理及日志量，包括部分未摇铃时的在线查询。按一种查询计算，2 秒一次约每秒 0.5 次；实际总量由游戏状态决定。少人数测试未观察到明显卡顿，不能保证所有电脑或多人负载均无影响。它不直接修改角色属性、剧情、存档和画质，也不改变战斗同步频率。

## 生效与恢复

新默认值只在新构建／部署的服务中生效；更新仓库源码不会自动重启现有服务器。游戏进入在线时获取 `ss.info`，更改服务参数后，两端应正常退出再启动，避免沿用旧参数。

- Linux：停止游戏后，在实际部署的 gameserver 命令中删除 `--summon-interval` 和后面的 `2`，或设为 `--summon-interval 0`，再按原部署方式重建该服务；不要改 shadNet 账号配置、数据库或网络。
- Windows：这是无缝模式启动参数，GUI 暂无单独切换开关。高级用户可在 `server.py` 的无缝游戏服务命令中把 `--summon-interval` 后的 `2` 改为 `0`，停止并重启无缝服务，再重开游戏。

`0` 沿用原模板 35／30 秒，正常启动不需要修改文件。不要改动普通模式账号、游戏存档或已完成的世界恢复记录。
