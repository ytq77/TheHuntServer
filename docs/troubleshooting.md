# 服务端分层排错

先记录客户端版本、服务端版本、测试时间、两个账号分别在哪台电脑，以及哪台是房主。每次只改变一个条件。不要因为一次连接失败同时改端口、代理、账号和存档。

## 1. 容器是否正常运行

在**本套服务的 Compose 目录**执行：

```bash
sudo docker compose ps
sudo docker compose logs --since 10m --tail 150 shadnet gameserver
sudo ss -lntup | grep -E ':(31413|31414|31415|20443|20444)\b'
```

应看到 31414 为 UDP，其余为 TCP，且监听在管理员设置的服务器 Tailscale IPv4 上。`address already in use` 表示端口被占用；`cannot assign requested address` 通常需要检查该 IP 是否确实属于服务器、Tailscale 是否已经启动。

本方案使用 Linux host 网络，不能靠 Compose 的 `ports:` 重映射修正服务自身的监听地址。应检查程序配置，详见 [Docker host 网络说明](https://docs.docker.com/engine/network/drivers/host/)。

## 2. 玩家是否能到达相应端口

在玩家 Windows PowerShell 执行，把占位符换为服务器实际 Tailscale IPv4：

```powershell
$serverIp = '填写服务器的 Tailscale IPv4'
31413,31415,20443,20444 | ForEach-Object {
    Test-NetConnection -ComputerName $serverIp -Port $_ -InformationLevel Quiet
}
```

这些结果只说明 **TCP** 能否建立连接，不测试 UDP 31414，也不检查登录或入房。HTTP `/status`、游戏服务 `ss.info` 可用于进一步确认请求到了正确的服务。

使用代理客户端时，核对服务器 Tailscale 地址和所用域名是否走正确路由。系统代理绕过规则并不自动证明 TUN、游戏加速器或程序自身的连接路径正确。不要仅凭代理软件的开关状态归因。

## 3. 标题界面提示未登录 PSN / 返回离线

先核对：

- The Hunt 的四个地址是否属于同一套 BBSC 部署，协议和端口是否正确。
- 账号是否创建在这套 shadNet 的数据库中；两台电脑是否使用不同账号。
- shadNet 日志是否出现成功认证，以及 BBSC 游戏服务是否收到游戏请求。
- 服务器生成的 `ss.info` 是否把四个 `api_SummonData*` 指向 **31415**，其他对应接口指向 **20443**。

这里的 PSN 文案是游戏对在线状态的提示，不能据此断定要去登录真实 PlayStation 账号。也不要把 Discord、公共 shadNet 和私人 shadNet 的凭据混用。

## 4. 双方持续寻找，没有入房

按顺序收集证据：

1. 两人是否真的进入在线，且连接同一服务器、客户端版本兼容。
2. 使用的是否为 BBSC 的**唤猎之铃 / 应猎之铃**，而非拿普通召唤机制代替测试。
3. 服务器是否记录双方端点，以及房间或召唤相关请求。
4. UDP 31414 是否收到请求并有正确格式的回复；服务镜像是否包含 STUN 兼容补丁。
5. 对端地址查询后，客户端之间是否继续建立游戏连接。
6. 两端是否都连接 BBSC Relay 20444；进入世界后模组消息是否继续传输。

`Authenticated`、HTTP 200 或主服务连接成功，都不能代替第 4–6 步。曾经的实际故障就是认证成功但新格式 STUN 被丢弃。

普通联机的原版召唤铃变灰，应先检查该区域 Boss、灵视和地点条件。不要把这一类游戏规则问题直接当成服务器故障。

## 5. 一台电脑通过路由器的 Tailscale 子网路由

这种电脑可能只有局域网 IP。Tailscale 的子网路由默认启用 SNAT，因此服务端看到的来源地址可能是路由器的 Tailscale 地址。这个现象本身不足以判定联机可用或不可用。参见 [Tailscale 子网路由文档](https://tailscale.com/docs/features/subnet-routers)。

需要分别确认：

- 玩家电脑到服务器的去程。
- 服务器和对端使用所通告地址时的回程。
- 子网路由是否已批准、相关设备是否接受路由、访问策略是否允许。
- 两端日志和服务器端点表实际通告了什么地址与端口。

先保存这些证据，再决定是否需要在该电脑直接安装 Tailscale 做对比。不要直接禁用 SNAT、全局更改默认路由或开放整个公网来试运气。

## 6. 能入房，但死亡 / 传送后断开或不同步

确认两台电脑使用同一套 The Hunt/BBSC 版本及配置，同时核对 20444 的连接和两端模组日志。客户端版本、模组加载和 Relay 都可能影响这一阶段，STUN 修复只解决此前发现的端点发现问题。

复验至少包括：双方移动、互相观察伤害、分别死亡、提灯复活与同行传送、Boss 战结束后的会话保持。单人在线一小时不等于双人路径全部通过。

## 提交问题时提供什么

提供客户端/服务端版本、发生时间（带时区）、两端的简短日志片段、对应容器日志、复现步骤和网络拓扑。先去掉密码、令牌、注册密钥、数据库内容和私人地址；不上传完整使用过的启动器目录、状态目录或抓包文件。

保留本地原始记录便于比对。日志里的旧警告不一定是本次失败的原因，要按同一时间窗口对齐两个客户端和服务器。
